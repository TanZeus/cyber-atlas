TrickyStore & Hardware Key Attestation

A control- and data-flow map of how Android hardware key attestation works, how TrickyStore forges it at the Keystore2/KeyMint boundary, how a leaked keybox turns a self-signed leaf into a Google-rooted chain, and why that yields Play Integrity STRONG. Written for OS-level understanding of the mechanism and its detection — not as an evasion recipe.

Keystore2 / KeyMint OID 1.3.6.1.4.1.11129.2.1.17 Play Integrity Educational · defensive
Executive summary
  1. Android key attestation lets a remote verifier trust a device by having secure hardware (TEE/StrongBox) sign a certificate whose extension states the boot state, patch level, and a caller-supplied challenge, chaining up to a Google-controlled root CA.
  2. TrickyStore is a root (KernelSU/Magisk + Zygisk) module that intercepts the certificate chain returned by keystore2/KeyMint and substitutes a forged chain before it reaches the app, so the forgery is app-agnostic and needs no per-app hooking.
  3. The enabling asset is a leaked "hardware" keybox — a Google-signed EC/RSA batch key plus its cert chain — which lets TrickyStore mint a fresh leaf that declares verifiedBootState = Verified (GREEN), deviceLocked = true and validates all the way to Google's attestation root.
  4. A target.txt allow-list decides which calling packages get a forged chain; non-listed apps fall through to the real TEE. Listing com.google.android.gms makes Play Integrity's own attestation use the forged chain, producing MEETS_STRONG_INTEGRITY.
  5. It defeats naive verifiers but not strong ones: Google revokes leaked keyboxes via a status/CRL list, ID-attestation and StrongBox expectations can mismatch, and freshness/RKP checks can still reject a forged-but-well-formed chain.

1Hardware key attestation from first principles

Key attestation answers one question for a remote party: "was this key really generated and held inside this device's secure hardware, on a device in a known boot state?" The app never sees the private key; instead the secure environment signs a certificate that describes the key and the device, and that certificate chains to a root the verifier already trusts.

1.1 The app-side API surface

An app requests attestation by generating a key with a challenge supplied by the verifier (the nonce that binds the attestation to a specific request):

KeyPairGenerator kpg = KeyPairGenerator.getInstance(
        KeyProperties.KEY_ALGORITHM_EC, "AndroidKeyStore");
kpg.initialize(new KeyGenParameterSpec.Builder(
        "attest_key",                       // alias
        KeyProperties.PURPOSE_SIGN)
    .setAlgorithmParameterSpec(new ECGenParameterSpec("secp256r1"))
    .setDigests(KeyProperties.DIGEST_SHA256)
    .setAttestationChallenge(serverNonce)   // <-- binds chain to verifier
    // .setIsStrongBoxBacked(true)          // request StrongBox (SE) vs TEE
    // .setAttestationIds(...)              // ID attestation (privileged)
    .build());
kpg.generateKeyPair();

Certificate[] chain = KeyStore.getInstance("AndroidKeyStore")
        .getCertificateChain("attest_key");

The returned chain is the deliverable. Its structure:

PositionCertificateSigned byCarries
Leaf (chain[0])Attestation cert for attest_keyDevice batch/attestation key (in TEE/StrongBox)The public key of attest_key + the attestation extension with the challenge and device state
Intermediate(s)Batch attestation cert / RKP-provisioned intermediatesHigher intermediate, ultimately GoogleModel/batch identity; on RKP devices, a device-unique provisioned key
RootGoogle Hardware Attestation Root CASelf-signed (public key published by Google)The trust anchor the verifier pins

1.2 The attestation extension — OID 1.3.6.1.4.1.11129.2.1.17

The heart of attestation is a non-critical X.509v3 extension embedded in the leaf certificate. Its ASN.1 KeyDescription carries the security level, two authorization lists (software-enforced and hardware/TEE-enforced), and — nested in the hardware list — the RootOfTrust. This is precisely the structure a forger must reproduce.

1.3 RootOfTrust — the fields the forgery overwrites

Inside the hardware-enforced list, tag 704 holds a RootOfTrust SEQUENCE. These four values are what a "leaf hack" or keybox forge rewrites to make an unlocked, rooted device look pristine:

ASN.1 fieldTypeHonest value on a rooted/unlocked deviceForged value
verifiedBootKeyOCTET STRINGCustom/AOSP key hashStock OEM key hash (or zeros)
deviceLockedBOOLEANfalse (bootloader unlocked)true
verifiedBootStateENUMERATEDUnverified(2)=ORANGE or SelfSigned(1)=YELLOWVerified(0)=GREEN
verifiedBootHashOCTET STRING (attestation v3+)Hash of the running (patched) boot imagePlausible stock hash

1.4 What a verifier does with the chain

  1. Path validation — verify each signature up to a pinned Google Hardware Attestation Root public key. A chain that doesn't reach that anchor is worthless.
  2. Challenge match — the attestationChallenge must equal the server nonce it just issued (freshness / anti-replay).
  3. Boot state policy — require verifiedBootState = Verified and deviceLocked = true.
  4. Security level policy — require TrustedEnvironment or StrongBox (reject Software).
  5. Freshness / patch level — reject stale osPatchLevel/bootPatchLevel.
  6. Revocation — check the leaf/intermediate serials against Google's attestation status list / CRL (android.googleapis.com/attestation/status). This is the step that catches leaked keyboxes.

2The keybox: the enabling asset

A keybox is the OEM-facing artifact used at the factory to provision a device's attestation identity. In TrickyStore it lives at /data/adb/tricky_store/keybox.xml. Structurally it is an XML file that, per algorithm, pairs a private key with the Google-signed certificate chain for that key:

<AndroidAttestation>
  <Keybox DeviceID="...">
    <Key algorithm="ecdsa">
      <PrivateKey format="pem"> ...EC private key... </PrivateKey>
      <CertificateChain>
        <Certificate> batch/leaf cert </Certificate>
        <Certificate> intermediate  </Certificate>
        <Certificate> Google root   </Certificate>
      </CertificateChain>
    </Key>
    <Key algorithm="rsa"> ... </Key>
  </Keybox>
</AndroidAttestation>

(Schematic only — no real key material is reproduced here.)

Why it is the enabling asset: the private key in the keybox is the signing capability that TrickyStore lacks on an unlocked device. Possessing it lets TrickyStore sign a freshly-minted leaf certificate so the chain terminates at Google's root — reproducing the one thing the TEE would otherwise do and refuse to do with GREEN boot state on an unlocked device.

"Hardware" / valid keyboxAOSP / software keybox
Chain terminates atGoogle Hardware Attestation RootAOSP test root (public, in AOSP tree)
Security level it can claimTrustedEnvironmentEffectively Software
Fools a strict verifier?Until revokedNo — anchor isn't trusted
ScarcityLeaked/rare; the whole gameFreely available
RevocationGoogle maintains an attestation status list (serving as a CRL) keyed by certificate serial number. Once a leaked keybox's serials are published there, any verifier that checks the list (Play Integrity does) will reject chains built from it. This is why leaked keyboxes have a shelf life and why "which keybox" matters more than "which module".

3TrickyStore architecture & interception point

3.1 Where it hooks, and why that location is app-agnostic

Attestation on Android 12+ flows App → keystore2 (the AIDL system service android.system.keystore2) → KeyMint HAL (in the TEE). TrickyStore is delivered as a root module (KernelSU or Magisk, using Zygisk-style native injection). It inserts itself at the keystore2 boundary and intercepts the operation that returns the certificate chain (key generation / attestKey), swapping the chain before it is handed back across Binder to the requesting app.

Because every app — a bank, a game, or Google Play Services — obtains attestation through the same keystore2 service, hooking there is app-agnostic: TrickyStore never touches the target app's process. It only needs to know which caller is asking (the UID/package on the Binder transaction) to decide whether to forge. This is the architectural reason a single module can cover arbitrary apps.

Precision noteThe exact injection primitive (which process is entered, and how the transaction is captured) is implementation- and version-specific and has changed across releases. The stable, load-bearing claim is the logical hook site: the certificate chain returned by keystore2/KeyMint for an attested key. Treat lower-level specifics as version-dependent.

4Targeting: the target.txt mechanism

target.txt is a newline-separated allow-list of calling package names. TrickyStore watches the file (inotify-style) and re-reads it on modification, so edits take effect without a reboot. Matching is on the identity of the process requesting attestation, resolved from the Binder caller's UID.

EntryEffect
com.example.bankForge attestation for this package (default mode)
com.example.bank!Trailing ! forces full keybox generation for this package (vs. the module's default/leaf behavior). (flag syntax is version-dependent)
com.google.android.gmsForge for Google Play Services — the linchpin for Play Integrity (Section 5)
(package absent)Falls through to the real TEE — honest boot state is returned

4.1 Why GMS must be listed for Play Integrity STRONG

Play Integrity's device verdict is produced by Google Play Services (the com.google.android.gms package; DroidGuard runs in com.google.android.gms.unstable), which itself performs a hardware-backed key attestation against Google's servers. Because TrickyStore matches on the calling package, GMS only receives a forged chain if com.google.android.gms is in target.txt. List it, and GMS's own attestation now reports GREEN/locked from a Google-rooted chain → MEETS_STRONG_INTEGRITY.

4.2 Why a self-attesting app must be listed explicitly

A banking or DRM app that calls the KeyStore API itself is a different caller than GMS. Forging GMS's attestation does nothing for that app's own getCertificateChain() result. The app's package must be added to target.txt in its own right, or it will get the real TEE chain (revealing the unlocked/rooted state).

5Relationship to Play Integrity (and PIF)

Play Integrity returns a deviceIntegrity field carrying zero or more labels. The three that matter here, in ascending strength:

LabelRoughly meansPrimary evidence
MEETS_BASIC_INTEGRITYA generic Android device, not obviously tamperedSoftware signals + plausible build fingerprint
MEETS_DEVICE_INTEGRITYA genuine, Play-certified deviceIncreasingly hardware-backed key attestation (esp. 2024+)
MEETS_STRONG_INTEGRITYGenuine device + recent security patch + verified boot, hardware-rootedHardware key attestation with GREEN/locked

5.1 Division of labour: PIF vs TrickyStore

These solve different checks and are usually stacked:

ComponentSpoofsTargets which check
Play Integrity Fix / Fork (PIF)Build fingerprint & system properties (ro.build.*, security patch, model) to a known Play-certified profileFingerprint/profile-based checks; historically enough for BASIC and sometimes DEVICE
TrickyStoreThe hardware key attestation certificate chain (boot state, lock state, Google-rooted signature)Hardware-attestation checks → DEVICE and STRONG

In short: PIF lies about what the device claims to be; TrickyStore lies about what the secure hardware certifies. Since Google moved DEVICE/STRONG onto hardware attestation, PIF alone no longer reaches STRONG — TrickyStore (with a valid keybox) is what carries it there. The boundary between what PIF vs TrickyStore is sufficient for has shifted over time and is version/date-dependent.

6Detection & failure modes

A forged chain can be well-formed and still be caught. The defenses layer:

DetectionMechanismWhy the forge fails
Keybox revocationVerifier checks leaf/intermediate serials against Google's attestation status list/CRLLeaked keybox serials get listed → chain rejected regardless of GREEN state
ID-attestation mismatchVerifier requests device ID attestation (IMEI/serial/brand-model tags)Keybox's batch identity / forged IDs don't match the real device; hard to keep self-consistent
StrongBox expectationVerifier requires securityLevel = StrongBox(2)Most leaked keyboxes / forges claim only TrustedEnvironment; a StrongBox-only policy rejects them
Patch-level freshnessReject stale osPatchLevel/bootPatchLevelsecurity_patch.txt must be kept current and internally consistent with the claimed fingerprint (PIF) — drift is a tell
RKP / provisioning methodNewer devices use Remote Key Provisioning; short-lived, Google-backend-issued certs look different from a static factory keybox chainA static keybox chain on a device that should be RKP-provisioned is anomalous
Consistency / behavioralServer correlates fingerprint, patch dates, boot hash, security level, and account/device historyA strict third-party (banking) verifier can reject a chain that validates but doesn't cohere
Key pointPath validation success is necessary, not sufficient. Google's own Play Integrity leans on revocation and server-side correlation, which is why fresh, unrevoked "hardware" keyboxes are the scarce resource and why a bank writing a strict verifier — pinning StrongBox, requiring ID attestation, and checking the status list — can still reject a forged-but-valid-looking chain.

7Android architecture (context)

The attestation trust model only makes sense against the layered platform it sits in. From the top down:

LayerContentsRelevance to attestation
AppsAPKs in per-UID sandboxesThe caller identity TrickyStore matches on
Java/System frameworkSystem services in system_server; the AndroidKeyStore providerAPI entry point (KeyPairGenerator, KeyStore)
Native services / HALkeystore2 daemon; KeyMint AIDL HALThe hook site
KernelLinux kernel + SELinux (enforcing), Binder IPC, dm-verityKernelSU operates here; dm-verity guards system integrity
Secure worldTrustZone TEE (KeyMint TA) and/or StrongBox secure elementHolds the real device attestation key; what the forge substitutes for
Boot chainBootloader → Android Verified Boot (AVB) → verified boot state (GREEN/YELLOW/ORANGE/RED)The exact state the extension reports and the forge rewrites

Android Verified Boot (AVB) cryptographically verifies each stage from the bootloader up. An unlocked bootloader or a modified boot image drives the state to YELLOW/ORANGE, and the TEE faithfully attests that — which is exactly the truth TrickyStore must overwrite. Remote Key Provisioning (RKP) is the newer model where attestation certs are provisioned per-device from Google's backend rather than baked in as a static factory keybox, shrinking the value of leaked keyboxes over time.

8Attacks on the Android architecture

TrickyStore is one entry in a broader family of platform-integrity attacks. Mapping them clarifies where attestation forging sits and what it depends on.

Attack classWhat it subvertsRelation to attestation forging
Bootloader unlockAVB chain of trustPrecondition for rooting; also what turns boot state non-GREEN — the thing TrickyStore hides
Systemless root (Magisk/KernelSU)Runs privileged code without modifying /system on disk (dodging dm-verity)Provides the privilege TrickyStore needs to inject at the keystore boundary
Zygisk / native injectionCode injection into system/app processes at zygote forkDelivery mechanism for TrickyStore and PIF
Property/fingerprint spoofing (PIF)Software identity signalsComplementary lie — covers the fingerprint checks attestation forging doesn't
SELinux policy weakeningMandatory access controlMay be needed for the module to reach protected interfaces
TEE / TrustZone exploitationThe secure world itselfA stronger attack: extract the real device key rather than borrow a leaked keybox — rare, high-value
Downgrade / rollbackVersion anti-rollback (patch level)Old firmware with known TEE bugs can expose keys or weaken checks; conflicts with freshness requirements
Keybox theft / leakageOEM provisioning secretsThe supply of the enabling asset — the root cause that makes full-generation mode possible

Read as a chain: unlock bootloader → systemless root → inject via Zygisk → forge attestation (TrickyStore + leaked keybox) + spoof identity (PIF). The defense that most reliably breaks the chain is not any single on-device check but Google's revocation of leaked keyboxes plus server-side correlation — the parts an on-device module cannot forge.

Glossary

AVB (Android Verified Boot)
Cryptographic verification of each boot stage; sets the verified boot state (GREEN/YELLOW/ORANGE/RED).
Attestation extension
X.509 extension (OID 1.3.6.1.4.1.11129.2.1.17) in the leaf cert carrying the challenge, security level, and RootOfTrust.
keystore2 / KeyMint
Android 12+ AIDL keystore service and its hardware HAL (TEE-resident), replacing legacy keystore/Keymaster.
Keybox
OEM provisioning artifact: attestation private key(s) + Google-signed cert chain. Leaked "hardware" keyboxes enable full forging.
RootOfTrust
ASN.1 SEQUENCE (tag 704): verifiedBootKey, deviceLocked, verifiedBootState, verifiedBootHash — the fields the forge overwrites.
StrongBox
A discrete secure element providing a higher security level than the TrustZone TEE.
RKP (Remote Key Provisioning)
Newer model where attestation certs are provisioned per-device from Google's backend rather than a static factory keybox.
Play Integrity verdicts
MEETS_BASIC_INTEGRITY / MEETS_DEVICE_INTEGRITY / MEETS_STRONG_INTEGRITY — STRONG requires hardware attestation with verified boot.
PIF (Play Integrity Fix/Fork)
Module that spoofs build fingerprint and system properties; complements TrickyStore's attestation forging.
TrickyStore
Root module that intercepts the keystore2/KeyMint certificate chain and substitutes a forged one for targeted packages.
