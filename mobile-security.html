Mobile Security — Android Attacks & Instrumentation

A single, in-depth map of Android from the security model down to the TEE: the full attack surface and every major attack class, the root-hiding / attestation-forging ecosystem (Magisk · KernelSU · Zygisk · PIF · TrickyStore), how to author your own KernelSU/Magisk modules, the theory of runtime hooking, and a working test-case catalog for Frida and Objection. Written for OS-level understanding on authorized targets — mechanisms and detection, not a recipe against any specific victim app.

OWASP MASVS / MASTG Keystore2 / KeyMint Frida · Objection KernelSU · Magisk · Zygisk Educational · authorized testing only
Executive summary
  1. Android's security rests on the Linux UID sandbox, SELinux MAC, app signing, and a hardware root of trust (Verified Boot → TEE/StrongBox). Most attacks are about escaping, spoofing, or observing across one of those boundaries.
  2. The app-layer attack surface is dominated by insecure storage, exported components/IPC, WebView, weak crypto/TLS, and broken auth/logic; the platform layer by bootloader unlock, root, and TEE issues.
  3. Rooting (Magisk/KernelSU) plus Zygisk injection is the delivery vehicle for integrity attacks; PIF spoofs identity and TrickyStore forges hardware key attestation to reach Play Integrity STRONG.
  4. Runtime hooking — Java/ART via Frida or Xposed/LSPosed, native via inline/PLT-GOT — is the central dynamic-analysis technique; Frida and Objection turn it into repeatable test cases (SSL-pinning bypass, root/emulator-detection bypass, crypto interception, tracing).
  5. Defenders answer with attestation, revocation, server-side correlation, RASP, and anti-instrumentation; each has known blind spots documented below.

1Android architecture & security model

Every mobile attack is easier to reason about against the layered platform. From the top down:

1.1 The five pillars

  • Application sandbox — each app gets a unique UID; the kernel's DAC keeps /data/data/<pkg> private. Same-signature apps can share a UID (sharedUserId, now deprecated).
  • SELinux (MAC) — type-enforcement domains (untrusted_app, system_server, keystore). Enforcing since Android 5; blocks many post-exploitation moves even with root.
  • App signing — v1 (JAR), v2/v3 (APK Signing Block, key rotation), v4 (streaming/fs-verity). Identity = signing key, not package name.
  • Verified Boot (AVB) — vbmeta signatures verify each stage; rollback protection via tamper-evident version counters. Drives the GREEN/YELLOW/ORANGE/RED state that attestation reports.
  • Hardware-backed keystore — keys live in the TEE/StrongBox; the framework only holds handles. Underpins attestation (Section 7).

3App-layer attacks (in depth)

3.1 Insecure data storage (M9)

Anything under /data/data/<pkg>/ is DAC-protected but trivially readable on a rooted/backup-enabled device. Common sinks and their tells:

3.2 IPC & exported components (M8)

The four component types are the primary local attack surface. A component is reachable by other apps if android:exported="true" (implicit-true when it declares an intent-filter on older targetSdk).

ComponentAbuseExample
ActivityLaunch privileged screen, bypass auth, tapjackingam start -n pkg/.AdminActivity skips the login gate

Broadcast ReceiverSpoof system events, inject stateFake "payment success" broadcast a receiver trusts

Intent attacks

  • Intent redirection / "intent hijack" — app forwards an attacker-supplied Intent (via getParcelableExtra) to a privileged internal component (confused deputy).
  • Implicit-intent eavesdropping — sensitive data broadcast implicitly is readable by any registered receiver.
  • PendingIntent hijack — a mutable PendingIntent handed to another app lets it fill in the blanks and act as the sender.
  • Deep-link / App-Link abuse — unvalidated https:///custom-scheme links drive internal navigation, oauth-token theft via open redirect, or WebView loads of attacker URLs.

3.4 Injection & crypto (M4, M10)

  • SQLi in providers — query() selection built by string concat; test via content query --uri.
  • Path traversal in providers exposing files by openFile().
  • Weak crypto — AES/ECB (pattern leakage), static IV, hardcoded keys in DEX/native, Random instead of SecureRandom, home-grown "encryption".
  • Insecure KDF — MD5/SHA-1 password hashing, no salt, low iteration counts.

3.5 Auth, session & business logic (M3)

  • Client-side-only auth / feature gating (unlocked by flipping a boolean — a prime hooking target, Section 11).
  • JWT flaws: alg:none, weak HMAC secret, no expiry/audience check.
  • Biometric bypass: result-only (boolean) callbacks not bound to a CryptoObject — hookable.
  • IDOR/BOLA at the API, replay of signed requests, race conditions in payment flows.
Testing postureMost of Section 3 is exercised statically (jadx/apktool, Section 6) then confirmed dynamically with ADB, Frida, and Objection (Sections 11–12) — e.g. dumping shared_prefs, calling exported components with am/content, and hooking the auth boolean.

4Platform & OS-level attacks

4.1 Bootloader & Verified Boot

  • Bootloader unlock (fastboot flashing unlock) wipes userdata and flips AVB to YELLOW/ORANGE — the precondition for custom images and root, and the state attestation reports honestly (until forged).
  • AVB downgrade / rollback — flashing older, vulnerable firmware; blocked by rollback counters where implemented.
  • vbmeta tampering — --disable-verity --disable-verification to run a modified boot image.

4.2 Rooting

MethodMechanismNote
MagiskPatches boot/init_boot ramdisk; "systemless" overlay; su daemon; MagiskHide removed, DenyList remainsUserspace root manager; Zygisk for injection
KernelSUKernel-space root via a custom kernel or GKI module; su granted by the kernel; app-profile basedHarder to detect from userspace; needs kernel source/GKI
APatchKernel patching approach similar in spirit to KernelSUAlternative kernel-based manager
Exploit-basedTemporary root via a kernel/vendor bug (e.g. Dirty COW-class)Device/version specific

4.3 Privilege escalation & the secure world

  • SELinux weakening — permissive domains or over-broad policy to reach protected sockets/services.
  • Confused-deputy via system_server — abusing a privileged service to act on the attacker's behalf.
  • TEE / TrustZone exploitation — memory-corruption in a Trusted Application to leak keys or forge attestation from inside the secure world (rare, high-value; e.g. historical QSEE/Trustonic bugs).
  • Secure-element / NFC and baseband attack surfaces for the well-resourced.
ChainThe canonical platform chain: unlock bootloader → flash/patch boot → systemless root → Zygisk injection → module-level integrity attacks (PIF + TrickyStore). Section 8 details the last stage; Section 9 shows how to author the modules.

5Network & transport attacks

5.1 Interception

  • Proxy MITM — Burp/mitmproxy with the CA installed. Since Android 7, apps trust only system CAs unless network_security_config opts into user CAs; a rooted device can push the CA to the system store (or Magisk "MoveCert"/cert-injection modules).
  • Cleartext — usesCleartextTraffic / missing NSC allows HTTP; downgrade and inject.

5.2 Certificate pinning

Pinning binds the server cert/key to the app, defeating proxy CAs. Bypass approaches (all require instrumentation, Sections 11–12):

7Hardware key attestation & TrickyStore

Key attestation answers, for a remote verifier: "was this key generated inside this device's secure hardware, in a known boot state?" The app never sees the private key; the TEE signs a certificate describing the key and device, chaining to a Google-controlled root.

7.1 App-side API and the returned chain

// challenge = server nonce; binds the attestation to one request
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC","AndroidKeyStore");
kpg.initialize(new KeyGenParameterSpec.Builder("attest_key",
        KeyProperties.PURPOSE_SIGN)
    .setAlgorithmParameterSpec(new ECGenParameterSpec("secp256r1"))
    .setDigests(KeyProperties.DIGEST_SHA256)
    .setAttestationChallenge(serverNonce)
    // .setIsStrongBoxBacked(true)   // StrongBox SE vs TrustZone TEE
    .build());
kpg.generateKeyPair();
Certificate[] chain = KeyStore.getInstance("AndroidKeyStore")
        .getCertificateChain("attest_key");   // leaf -> intermediates -> Google root

7.3 The keybox — the enabling asset

A keybox (/data/adb/tricky_store/keybox.xml) pairs, per algorithm, a private key with its Google-signed cert chain:

<AndroidAttestation><Keybox DeviceID="...">
  <Key algorithm="ecdsa">
    <PrivateKey format="pem"> ...EC private key... </PrivateKey>
    <CertificateChain>
      <Certificate> batch/leaf </Certificate>
      <Certificate> intermediate </Certificate>
      <Certificate> Google root </Certificate>
    </CertificateChain>
  </Key>
  <Key algorithm="rsa"> ... </Key>
</Keybox></AndroidAttestation>   // schematic — no real key material

The keybox private key is the signing capability an unlocked device otherwise lacks. With it, TrickyStore mints a leaf declaring GREEN/locked and chains to Google's root. A "hardware" keybox chains to the Google root (claims TrustedEnvironment); an AOSP/software keybox chains only to the public AOSP test root and fools nothing strict.

RevocationGoogle publishes an attestation status list / CRL keyed by certificate serial (android.googleapis.com/attestation/status). Once a leaked keybox's serials are listed, chains built from it are rejected regardless of GREEN state — the reason leaked keyboxes have a shelf life.

7.4 TrickyStore: interception point & modes

Attestation flows App → keystore2 (AIDL android.system.keystore2) → KeyMint HAL. TrickyStore (a KernelSU/Magisk + Zygisk module) inserts at the keystore2 boundary and substitutes the certificate chain returned for a targeted caller before it crosses Binder back to the app. Because every app attests through the same service, the hook is app-agnostic.

Precision noteThe exact injection primitive is version-specific and has changed across releases. The stable claim is the logical hook site: the chain returned by keystore2/KeyMint for an attested key.
Leaf hack (no keybox)Full generation (keybox)
ChangesRewrites RootOfTrust fields, re-signs leafMints new GREEN/locked leaf, signs with keybox key, appends Google chain
Chain anchorBroken (re-sign invalidates path)Valid to Google root (until revoked)
FoolsVerifiers reading boot fields but not validating chainFull-validation verifiers (Play Integrity)

State it maintains under /data/adb/tricky_store/: keybox.xml, target.txt, security_patch.txt (patch-level overrides), a TEE status probe, and working key_db state.

7.5 Targeting — target.txt

A newline-separated allow-list of calling packages, watched and re-read on change. Non-listed callers fall through to the real TEE (honest state). A trailing ! forces full keybox generation for that package (flag syntax is version-dependent). Listing com.google.android.gms is the linchpin for Play Integrity STRONG: the device verdict is produced by GMS (DroidGuard in com.google.android.gms.unstable), which does its own hardware attestation — only forged if GMS is targeted. A self-attesting bank app is a different caller and must be listed in its own right.

7.6 Play Integrity relationship & PIF

LabelMeansPrimary evidence
MEETS_BASIC_INTEGRITYGeneric, not obviously tamperedSoftware signals + plausible fingerprint
MEETS_DEVICE_INTEGRITYGenuine Play-certified deviceIncreasingly hardware-backed attestation
MEETS_STRONG_INTEGRITYGenuine + recent patch + verified bootHardware key attestation

PIF lies about what the device claims to be (spoofs ro.build.* fingerprint/props); TrickyStore lies about what the secure hardware certifies (the attestation chain). Since Google moved DEVICE/STRONG onto hardware attestation, PIF alone no longer reaches STRONG — TrickyStore with an unrevoked keybox carries it there. The exact sufficiency boundary is date/version-dependent.

9Building KernelSU / Magisk modules

Magisk and KernelSU share a flashable-module format and script lifecycle, so one module often runs on both. A module is a ZIP with a defined layout; the manager mounts it "systemless" (overlaid, never touching the real partitions) and runs its scripts at boot stages.

9.1 Module layout

my-module.zip
├─ module.prop            # identity/metadata (required)
├─ META-INF/com/google/android/
│   ├─ update-binary      # stock installer stub (copy from template)
│   └─ updater-script     # must contain: #MAGISK
├─ customize.sh           # install-time logic (optional)
├─ post-fs-data.sh        # runs early, pre-Zygote, blocking
├─ service.sh            # runs late_start (post-boot), non-blocking
├─ uninstall.sh           # cleanup on removal
├─ system/                # files overlaid onto /system (systemless)
│   └─ ...
├─ system.prop            # resetprop key=value applied at boot
├─ sepolicy.rule          # custom SELinux rules (magiskpolicy)
└─ zygisk/                # Zygisk native libs (arm64-v8a/, x86_64/) if any

9.3 Systemless file replacement

Anything under the module's system/ is overlaid at the matching path. To ship a file to /system/etc/hosts, place it at system/etc/hosts in the module. Use a .replace empty folder to fully mask a stock directory. This is how a "MoveCert" module injects a CA into the system trust store without a writable /system.

9.4 Zygisk modules (native injection + companion)

Zygisk modules run native code inside every forked app/system process. This is what PIF and Shamiko use. Skeleton:

// C++ against the Zygisk API header (zygisk.hpp)
class DemoModule : public zygisk::ModuleBase {
  void onLoad(zygisk::Api *api, JNIEnv *env) override { this->api=api; this->env=env; }
  // called before app specialization: decide per-process action
  void preAppSpecialize(zygisk::AppSpecializeArgs *args) override {
     const char *pkg = env->GetStringUTFChars(args->nice_name, nullptr);
     if (strcmp(pkg,"com.target.app")==0) { /* set up hooks / spoof here */ }
     // request unload if not needed, to shrink footprint & detection
     api->setOption(zygisk::DLCLOSE_MODULE_LIBRARY);
  }
  void postAppSpecialize(const zygisk::AppSpecializeArgs *) override {}
private: zygisk::Api *api; JNIEnv *env;
};
REGISTER_ZYGISK_MODULE(DemoModule)
// heavy/root work is delegated to a "companion" running in the Magisk daemon:
REGISTER_ZYGISK_COMPANION(demo_companion)

Key ideas: preAppSpecialize lets you branch on the target package; the companion process (in the privileged daemon) does root-level work and passes results back over a socket, since the injected process itself is unprivileged. PLT/inline hooks are typically installed here.

9.5 KernelSU specifics

  • Root is granted by the kernel, and app access is governed by KernelSU's app-profile (per-UID su policy + SELinux context), not a userspace daemon.
  • Requires a KernelSU-patched kernel or a GKI (Generic Kernel Image) module — more setup than Magisk but harder to detect from userspace.
  • Module format is Magisk-compatible; KernelSU adds boot-completed and a WebUI (webroot/index.html) for module UIs.
  • post-mount.sh / umount hooks assist hiding from DenyList-style targets.
Test loopBuild the ZIP, adb push, flash via the manager (or magisk --install-module / KernelSU CLI), reboot, then verify with logcat, resetprop reads, and the app's own behavior. Keep modules minimal — every injected library is a detection surface (Section 13).

10Hooking — theory

Hooking = intercepting a function call to observe or alter its arguments, return value, or side effects at runtime. On Android there are two worlds — managed (Java/Kotlin on ART) and native (C/C++ in .so) — and different mechanics for each.

10.1 Java / ART hooking

TechniqueHowTooling
Method entrypoint swapReplace the ArtMethod's compiled/interpreter entrypoint or mark it native and trampolineFrida (Java API), Xposed/LSPosed, YAHFA, Dobby-based
Xposed-stylefindAndHookMethod with before/after callbacks; framework rewrites the methodLSPosed (Zygisk), EdXposed
Dynamic proxy / reflectionWrap interfaces, swap fields via reflectionFrida Java.use/Java.choose

Frida's Java.perform resolves classes via the runtime, replaces a method's implementation with a JS closure, and hands you this, the original method, and typed arguments. It works because ART lets a loaded agent rewrite method entrypoints in-process.

10.2 Native hooking

TechniqueMechanismCatches
PLT/GOT hookRewrite the Global Offset Table entry so calls to an imported symbol jump to your stubOnly calls that go through the PLT (imported/exported)
Inline (trampoline) hookOverwrite the first instructions of the target with a jump; relocate the originalsAny address, incl. internal/static functions
Import/Export by symbolResolve via dlsym / module exports, then Interceptor.attachExported functions (e.g. SSL_read)
Stalker (tracing)Dynamic recompilation of instruction streamsCoverage/tracing without static patches

Frida's Interceptor.attach(addr, {onEnter, onLeave}) is an inline-hook engine; Interceptor.replace swaps a whole function; Module.getExportByName resolves symbols. For internal native functions with no symbol, you pattern-scan (Memory.scan) for a byte signature — the standard approach for Flutter/BoringSSL pinning.

Diagram J — hooking taxonomy: two worlds, matching mechanics
flowchart TD
  ROOT["Runtime hooking"] --> J["Managed (Java/ART)"]
  ROOT --> N["Native (.so)"]
  J --> J1["Entrypoint swap\n(Frida Java.use)"]
  J --> J2["Xposed API\n(LSPosed)"]
  N --> N1["PLT/GOT rewrite"]
  N --> N2["Inline trampoline\n(Interceptor.attach)"]
  N --> N3["Pattern scan\n(Memory.scan) for\nunsymboled funcs"]
  N --> N4["Stalker tracing"]

10.3 Injection: how the agent gets in

  • frida-server (rooted) — a daemon runs as root; the client attaches/spawns and injects the agent via ptrace. Most flexible.
  • frida-gadget (no root) — a shared library embedded into a repackaged APK (add to lib/, load early); runs inside the app with no separate server.
  • Zygisk/LSPosed — persistent, boot-time hooking framework (Section 9.4).
  • ptrace/LD_PRELOAD — classic native injection primitives underneath the above.

11.1 Setup & the two attach modes

11.2 Test case — universal-ish SSL pinning bypass (OkHttp + TrustManager)

Java.perform(function () {
  // OkHttp CertificatePinner.check() -> no-op
  try {
    var CP = Java.use('okhttp3.CertificatePinner');
    CP.check.overload('java.lang.String','java.util.List').implementation = function () {
      console.log('[+] OkHttp pinning bypassed'); return;
    };
  } catch (e) {}
  // Replace the default TrustManager with an all-trusting one
  var X509TM = Java.use('javax.net.ssl.X509TrustManager');
  var SSLContext = Java.use('javax.net.ssl.SSLContext');
  var TM = Java.registerClass({
    name: 'org.test.TrustAll',
    implements: [X509TM],
    methods: {
      checkClientTrusted: function () {},
      checkServerTrusted: function () {},
      getAcceptedIssuers: function () { return []; }
    }
  });
  var init = SSLContext.init.overload(
    '[Ljavax.net.ssl.KeyManager;','[Ljavax.net.ssl.TrustManager;','java.security.SecureRandom');
  init.implementation = function (km, tm, sr) {
    console.log('[+] SSLContext.init hooked -> injecting TrustAll');
    init.call(this, km, [TM.$new()], sr);
  };
});

For native/BoringSSL or Flutter pinning, this Java hook won't fire — fall back to a native Interceptor (11.6) or a maintained "universal unpinning" script.

11.3 Test case — root / emulator detection bypass

Java.perform(function () {

13Detection & anti-instrumentation

Apps and servers push back at three layers. Knowing the checks is both the offense (what to expect) and the defense (what to deploy).

13.2 Server-side: the checks a strong verifier keeps

DefenseWhy forgery can still fail
Keybox revocation (status list/CRL)Leaked keybox serials get listed → forged chain rejected regardless of GREEN
ID attestationRequested device IDs must match; keybox batch identity / forged IDs are hard to keep consistent
StrongBox requirementMost forges claim only TrustedEnvironment; a StrongBox-only policy rejects them
Patch-level freshnesssecurity_patch.txt must stay current and consistent with the spoofed fingerprint — drift is a tell
RKP / provisioning shapeA static factory-keybox chain on an RKP device is anomalous
Server correlationFingerprint, patch dates, boot hash, security level, account/device history cross-checked
Key takeawayPath-validation success is necessary, not sufficient. The controls an on-device module cannot forge — Google's revocation and server-side correlation — are what ultimately break the chain. A bank pinning StrongBox, requiring ID attestation, and checking the status list can reject a forged-but-well-formed chain that fools a naive verifier.

Glossary

AVB (Android Verified Boot)
Cryptographic verification of each boot stage; sets verified-boot state (GREEN/YELLOW/ORANGE/RED).
MASVS / MASTG
OWASP Mobile App Security Verification Standard & Testing Guide — the control/test reference.
keystore2 / KeyMint
Android 12+ AIDL keystore service and its TEE-resident HAL, replacing legacy keystore/Keymaster.
Attestation extension
X.509 extension OID 1.3.6.1.4.1.11129.2.1.17 in the leaf cert; carries challenge, security level, RootOfTrust.
RootOfTrust
ASN.1 SEQUENCE (tag 704): verifiedBootKey, deviceLocked, verifiedBootState, verifiedBootHash — the forged fields.
Keybox
OEM provisioning artifact: attestation private key + Google-signed chain. Leaked "hardware" keyboxes enable full forging.
StrongBox / RKP
Discrete secure element (higher assurance than TEE); Remote Key Provisioning issues per-device certs from Google's backend.
Magisk / KernelSU / Zygisk
Userspace root manager / kernel-space root / zygote-fork native injection framework.
PIF / TrickyStore
Module spoofing build fingerprint/props / module forging the hardware attestation chain.
Hooking
Runtime interception of a call to observe/alter it; Java (ART entrypoint swap) or native (PLT-GOT / inline).
Frida / Objection
Dynamic instrumentation toolkit / Frida-powered runtime toolkit packaging common mobile test cases.
frida-server / frida-gadget
Root daemon injecting agents / embeddable library for non-rooted, repackaged APKs.
RASP
Runtime Application Self-Protection — in-app root/hook/integrity detection.
Educational reference on Android platform-security internals, offensive techniques, and their detection, for authorized testing and defense. Contains no leaked keybox material, private keys, or per-victim evasion recipe. Version-specific behavior (attestation versions, Play Integrity thresholds, module flag syntax, RKP adoption, Frida/Objection command surfaces) evolves — treat exact internals as time-dependent and verify against current tool docs.
